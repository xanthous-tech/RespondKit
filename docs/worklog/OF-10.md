## Implementation decisions

Two boundary designs were considered: synchronous draft posting from the API with a durable receipt, or workflow-owned posting and approval waiting. The latter was selected so Discord retries remain in durable steps and accepted replies share one publication/email/audit pipeline. An immutable D1 receipt freezes the first request before Workflow creation; an ambiguous create can be retried with the same key. No new scheduler, queue, or assignment interface was added.

Credentials are stored as SHA-256 digests in `AGENT_TOKEN_<inboxId>`, with constant-time comparison of fixed-size digests. A server-configured `AGENT_NAME_<inboxId>` supplies provenance. `X-Agent-Run-Id` distinguishes concurrent holders of the single inbox credential. Claims, release, close, and reopen use conditional database updates; drafts are invalidated transactionally when the conversation changes. Translation that needs review has a separate allowlisted Discord approval action.

Cloudflare references checked during implementation: [constant-time comparison](https://developers.cloudflare.com/workers/examples/protect-against-timing-attacks/) and [Workflow events, including events sent before the wait](https://developers.cloudflare.com/workflows/build/events-and-parameters/).

Limitations documented in v0: one credential per inbox grants both send and draft; no draft-only permissions; transcripts are paginated; leases coordinate runners sharing that credential; failed retained workflows require explicit recovery; approval waits expire after seven days; Discord reconciliation retains the existing bounded-history limitation.
