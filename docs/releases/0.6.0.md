# RespondKit 0.6.0

Status: prepared, not published. This document is the release-note draft and operator checklist. A version bump or merged PR does not deploy the API or publish SDK artifacts.

## Release notes

RespondKit 0.6.0 adds a React Native client and brings email follow-up and file attachments to support conversations across web, SwiftUI, Android Compose, and React Native.

- **React Native client:** native React Native UI, conversation history, read acknowledgements, draft persistence, identity isolation, device context, and native photo/file pickers. The file-picker module requires a native build; use an Expo development build rather than Expo Go.
- **Thread email:** configure a sender per site/app inbox. Unread operator messages are emailed after a default ten-minute delay, and reading them cancels pending delivery. Replies to the email return to the same customer thread. The minute-based sender normally delivers after 10–11 minutes; emails already handed to the provider cannot be recalled.
- **Client improvements:** configurable greeting for a fresh session, email collection when no address is known, and native device/OS diagnostics.
- **Attachments:** multiple files through web file inputs and system photo/document pickers on native clients, stored in private R2. Completed files have no product expiration or configured product size cap; platform limits still apply. Inbound email attachments are not supported.
- **Operator and developer tools:** optional conversation translation, Discord customer-activity links, refreshed human and agent-readable documentation, and private Paraglide compilers for Apple String Catalogs and Android resources.

AI support-agent credentials/jobs/reply APIs remain a proposal. Localization compilers generate resources, but translated SDK controls and UI language selection are not yet integrated. Host-provided titles/greetings remain host-localized.

## Upgrade and compatibility

Use the shared `0.6.0` version for all four npm packages, `dev.respondkit:respondkit-core`, `dev.respondkit:respondkit-compose`, and SwiftPM tag `v0.6.0` after publication is verified. SwiftUI requires Swift 6 and iOS 18+; Compose requires Android API 26+. React Native peers and installation steps are in its [README](../../packages/react-native/README.md).

Deploy the compatible API and migrations before rolling out SDK upgrades. Keep old SDKs working during the transition and first upgrade one pilot app. Do not claim email/files work until the target environment has their provider configuration and passes a live smoke test.

## Before creating the release

1. Merge the release-preparation PR after its npm, Swift, Android, and localization checks pass. Verify all manifests and `VERSION` are 0.6.0. The [shared process](../native/releases.md) lists local and CI gates.
2. Review and apply outstanding D1 migrations through `0007_attachments.sql` in the serving environment. This includes email routes, device context, email scheduling, and attachments. `api.respondkit.dev` is currently configured under Wrangler's `staging` environment; do not assume an environment named `production` exists.
3. Provision the private R2 bucket and `ATTACHMENTS` binding. Configure verified Cloudflare Email Sending, the `EMAIL` binding, inbound routing, and per-inbox sender/reply-domain settings. The checked-in Wrangler file currently lacks these two bindings. Retain the minute cron. See [email setup](../integrations/cloudflare-email.md) and [attachments](../integrations/attachments.md).
4. Deploy and smoke-test the API, then deploy the updated documentation site. Test unread delivery, read-before-deadline cancellation, inbound email replies, file upload/download and retry, and account isolation with a pilot inbox. Repository tests do not verify live DNS, email access, or R2 provisioning.
5. Confirm npm owner/2FA access for the first React Native publication and the existing Maven credentials. Prepare access to the release workflow's verified tarball artifact. No bootstrap package is published during preparation.

## Publish and verify

Create the `v0.6.0` tag on the reviewed release commit and publish its GitHub release using the Release notes section above. The release event runs verification and npm preflight before npm/Maven publication. Complete the [React Native first-publication procedure](../npm-publishing.md#react-natives-first-publication) using that run's verified tarball, then rerun failed jobs with the original artifacts.

Verify all four npm packages resolve to 0.6.0, both Maven coordinates are available, and SwiftPM resolves the tag. Install the registry artifacts in the pilot apps and test the real support flow before expanding rollout. Keep the Git tag and published versions immutable; registry publication is not atomic across npm and Maven.

The release workflow does not deploy Cloudflare Workers, run remote D1 migrations, configure email/R2, or update host apps. Those deployment steps must be completed explicitly. This checklist records required work; it is not evidence that the live environment has already been configured.
