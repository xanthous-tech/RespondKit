# npm publishing

RespondKit 0.6.0 publishes four public packages in dependency order:

1. `@respondkit/protocol`
2. `@respondkit/api-client`
3. `@respondkit/react`
4. `@respondkit/react-native`

The packages keep direct TypeScript source exports inside this pnpm workspace. `publishConfig.exports` rewrites npm tarballs to compiled ESM and declarations generated by Vite+ Pack. React retains selected sources for Tailwind CSS v4 scanning. React Native includes its native file-picker module, podspec, Android sources, and autolinking configuration. The Paraglide resource compilers remain private workspace tools.

## Local release gate

```sh
pnpm release:check
pnpm ready
pnpm build:npm
pnpm check:npm
pnpm pack:npm
```

Vite+ Pack runs publint and Are the Types Wrong. `check:npm` installs all four real tarballs into a temporary npm consumer, checks types and runtime imports, builds a React widget with Tailwind, and verifies licenses and package manifests. Native build and publication-consumer checks run in CI. `test:release` covers publication order, bootstrapping, matching and conflicting published artifacts, and registry failures.

## React Native's first publication

At the 2026-10-04 audit, the first three packages were published at 0.5.3, while `@respondkit/react-native` returned 404. Its initial authenticated publication and trusted-publisher setup are part of the actual 0.6.0 release, not release preparation. Do not publish a placeholder or rewrite a tarball to reserve the name.

The release workflow uploads its verified `npm-packages` artifact, then runs a read-only npm preflight **before either registry publication job**. A missing package stops preflight with bootstrap instructions. This lets the first publication use the exact verified release artifact; SwiftPM's Git tag already exists at this point.

When authorized to release:

1. Download the `npm-packages` artifact from the release workflow run (not an older PR run). Preserve these exact tarballs for recovery.
2. Authenticate to npm with access to the `respondkit` organization and complete the first React Native publication from outside this pnpm repository. For example, with the artifact extracted into `/tmp/respondkit-0.6.0-npm`:

   ```sh
   cd /tmp
   npm login
   npm publish /tmp/respondkit-0.6.0-npm/respondkit-react-native-0.6.0.tgz --access public
   ```

3. Configure its trusted publisher on npm: GitHub organization `xanthous-tech`, repository `RespondKit`, workflow `publish.yml`, allowed action `npm publish`. Confirm the existing three packages still trust that workflow.
4. Re-run the **failed jobs** in the original release workflow. Do not rebuild or repack the tarballs. Preflight recognizes the matching React Native artifact; the publish job skips it and publishes the remaining packages in dependency order.

React Native depends on the other 0.6.0 packages, so the bootstrap alone is not a usable completed release. Finish and verify the coordinated release before announcing availability. npm authentication/2FA and package settings need the account owner's publishing access; merely preparing or merging a PR does not configure them.

## Trusted publishing and recovery

Existing packages use GitHub OIDC, with no long-lived npm token. The publisher runs `npm` outside the checkout to honor the repository's pnpm `devEngines` setting. Pull requests do not publish. Publishing a GitHub release triggers registry publication after all verification and preflight gates pass.

`scripts/publish-npm.mjs --check <artifact-directory> v0.6.0` is read-only. It requires all four tarballs, verifies every package exists, and compares any already-published version's `dist.integrity` with the local SHA-512. Only an exact match is skipped. A conflicting artifact or registry/network failure stops the plan before any npm publish occurs. This checks artifact identity and package existence, not the account's OIDC permissions.

The `--publish` mode repeats the preflight and publishes only missing versions. Use it only as part of an authorized release. If a registry publish fails midway, retry the failed job using its original uploaded artifacts; do not rerun successful publishing jobs or move the Git tag. npm and Maven are not a single transaction.

For later releases, run `pnpm version:set <version>`, update the lockfile, pass the gates, merge, and publish the matching `v<version>` GitHub release. See the [shared release process](native/releases.md) and [0.6.0 release notes and operator checklist](releases/0.6.0.md).

Reference: [npm trusted publishing](https://docs.npmjs.com/trusted-publishers/).
